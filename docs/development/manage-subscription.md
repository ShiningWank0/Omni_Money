# サブスク管理機能の開発仕様

更新日: 2026-11-13。対象の統合ブランチ: `feat/manage-subscription`。

本書は統合ブランチで開発・レビューするための文書であり、mainの製品機能を説明するものではない。「確定」は利用者が指定した仕様、「実装提案」はレビューする内容を表す。2026-11-13に実装とPR作成の依頼を受けた。実装済みの操作と保存の契約は[利用ガイド](../how-to-use.md#サブスクの自動登録)、[API](../api-errors.md#サブスク管理と自動登録)、[Agent.md](../../Agent.md)へ反映する。VERSION更新・main向けPR・マージ・CI/CD継続監視は今回行わない。

## 0. 初期版の実装判断

利用者が確認した初期方針は、既存の手動支出から登録、短い月は月末へ補正、ルール単位のタイムゾーン、再開時に次回支払日を確認、削除した支払回は再作成しない、である。追加依頼により外貨サブスクの自動円換算も対象とする。

- 元の取引は手動のまま保持し、その翌月・翌年以降を初回支払回にする。新規登録で当日より前の日付を指定しない。周期変更時は、元の取引または生成済み支払いと同じ月・年の再発行を拒否する。
- 月額は元の基準日、年額は元の月日を保持し、短い月・平年の2月29日を月末へ寄せる。IANA timezoneをルール内に保存する。
- ルール256件、補完1要求24件・15秒、月表示0001年～9998年、履歴100件単位。候補は直近5,000件から同じ口座・項目・金額の3回連続、日付差3日以内を対象とし、生成済み・リンク済み・銀行側・既存ルールを除外する。拒否は同じパターンに継続適用する。
- 通貨はJPY・USD・EUR・GBP・AUD・CAD・CHF・CNY・HKD・SGD。元金額はdecimal文字列とし、外貨は小数2桁。Frankfurter v2のECB providerから支払日以前7日以内の最新日次参照レートを取得し、rational演算で円へ四捨五入する。固定HTTPS origin・redirect禁止・proxy不使用・timeout・サイズ制限・pair/date/decimal検証を使用し、通貨と日付だけを送信する。元金額・rate・公表日をvault内の支払回へ固定する。取得できない回は次回再試行する。
- CSV v3はサブスク拡張を含まない範囲を明示する。appendは手動取引、replaceは既存ルールを停止し、削除した取引・タグの参照を切り離す。処理済み支払回は保持する。完全なサブスク復元はschema 7のsnapshot/whole-data-root backupで行う。
- 一覧・履歴・カレンダーの自動登録取引にopacity .55を適用する。説明文字・バッジ・tooltip・専用色は追加しない。保存が失敗・未完了なら解除せず、serverのcompletedと同じtransactionで確認状態を確定する。

後続の節は元の確定条件と実装検討の記録として保持する。本書の削除はmain統合前に利用者の確認を受けて行う。

## 1. 目的と対象

資金項目を月額または年額のサブスクとして指定し、その周期に従って取引を自動登録する。指定済みのサブスクを一覧で管理し、支払日を月表示のカレンダーで確認できるようにする。既存の取引履歴からサブスク候補を提案する機能も対象に含む。

本書では、取引一覧に表示される資金項目を「取引」、自動登録の設定を「サブスクルール」、ある回の支払いを「支払回」と呼ぶ。

参考は[サブスクBox](https://apps.apple.com/jp/app/%E3%82%B5%E3%83%96%E3%82%B9%E3%82%AFbox/id6763571602)。同アプリの全機能の再現は対象にしない。カード情報の登録、銀行・カード会社との同期、外部サービスの自動解約、契約変更や決済の実行は追加しない。既存の口座・クレジットカード取引の扱いは維持する。

## 2. 確定した仕様

| 項目 | 決定内容 |
| --- | --- |
| 周期 | 月額・年額のサブスクを指定できる |
| 自動登録 | サブスクの性質に従い、通常の取引として登録する |
| 集計 | 自動登録直後から通常の取引と同様に残高・収支集計へ含める |
| 登録範囲 | 支払予定日が当日までの分を登録する。未来の分を取引として先に作らない |
| 未起動・ロック中 | その間の未登録分は、次回利用時に保管庫が利用可能になってから補う |
| 直後の表示 | 色味を変えず、透明度を高めて薄く表示する |
| 文字による状態説明 | 自動登録取引の確認状態を説明する文字・ラベル・バッジ・ツールチップ・補助説明を追加しない。必須条件であり、説明文の追加によって代替しない |
| 通常表示への変更 | 利用者がその取引を開いて保存したとき、または編集して保存したときに通常表示にする |
| 管理画面 | 自動登録の対象を一元管理し、自動登録を停止できる |
| 停止後の履歴 | すでに登録した取引を削除しない |
| 履歴検索 | 管理画面から、選択したサブスクの自動登録によって作られた取引だけを検索・表示できる |
| カレンダー | 月表示のみ。前月・翌月に加え、過去・未来の任意の月へ移動できる |
| 候補提案 | 明示指定がない取引について、サブスク指定するかを利用者に提案する |

実装上の状態名を本書や内部データで使用しても、それを製品画面の説明文へ転用しない。既存の項目名・金額・日付・保存ボタンなどは通常どおり表示する。サブスク指定の候補提案自体は要求された機能として設ける。

## 3. 表示と保存の契約

自動登録取引には、登録元の情報と表示上の確認状態を別々に保持する。通常表示になった後も登録元を保持し、管理画面からの検索を継続できるようにする。

| 操作・状態 | 表示・保存結果 |
| --- | --- |
| 通常の手動登録取引 | 既存の通常表示を維持する |
| サブスクから自動登録した直後 | 元の色を維持し、透明度だけで薄く表示する。取引の値と集計は通常どおり扱う |
| 詳細を開くだけ、キャンセル、閉じる | 薄い表示を維持する |
| 値を変えずに保存し、保存が成功 | 通常表示になる |
| 金額・日付などを編集して保存が成功 | 編集を反映し、通常表示になる |
| 保存失敗・取消・処理未完了 | 保存成功として扱わず、確認状態を変更しない |
| 一度通常表示になった取引の再表示 | 再起動・再ログイン後も通常表示を維持する |

透明度の具体値・適用範囲は、既存UIの通常表示と並べてUI用PRで確認する。専用色、色相の変更、状態を説明する新しい文字表示は採用しない。薄さを理由にクリックや編集を無効化しない。カレンダー内の自動登録取引でも、この表示条件を守る。

既存の保存ボタンで値を変えずに保存した場合も、確認状態を永続化できるようにする。serverで保存受付の応答を受けただけでは完了としない。[既存の保存受付](../../backend/database/transaction_save_schema.go)のcompletedと、取引変更・確認状態変更の確定を整合させる。Desktopでも、成功前の楽観的な状態変更だけで通常表示にしない。

## 4. 登録・管理・検索の操作

### 4.1. 手動指定

既存取引を起点に、周期、次回支払日、金額、口座、項目名などを確認してサブスクルールを作成できる設計とする。指定元の取引は手動取引のまま保持し、サブスク指定しただけで複製・再登録・薄い表示への変更を行わない。

起点となる取引とは別にルールを保持する。過去の取引を編集しただけで、将来の自動登録条件を無断で書き換えない。取引の個別編集とルールの編集を区別する。

### 4.2. 一元管理

管理画面では、サブスク名、月額・年額の別、金額、口座、次回支払日、自動登録の有効・停止を確認できるようにする。ルールの編集、停止、そのルールから生成した取引の表示を操作できるようにする。

停止はOmni Moneyへの新しい自動登録を止める操作とする。外部サービスの契約を解約する処理は持たない。停止済みのルールからも過去の自動登録取引へアクセスできる構成を検討する。

初期提案として、停止時点から新しい生成を止め、停止中の分は再開時に無断でまとめて登録しない。停止と生成が競合した場合の確定順はDBトランザクションで決める。再開時の次回支払日と、過去分の補完を許す操作の有無は実装前に確認する。

### 4.3. 生成元による検索

項目名の部分一致ではなく、保存されたルールID・生成元情報で絞る。そのルールから実際に自動生成した取引だけを対象にし、似た名前の手動取引や、指定の起点となった手動取引を混ぜない。

利用者が金額・日付・項目名を変更した後や、通常表示になった後も対象に含める。ルールが停止済みでも絞り込みを維持する。既存の口座・期間などの検索条件との組み合わせ、並び順、ページングも設計対象とする。

## 5. 周期・日付の実装提案

以下の端数日・時間帯の扱いは実装提案であり、確定仕様とは分けてレビューする。

| ケース | 初期提案 |
| --- | --- |
| 月額・通常日 | 元の基準日を維持し、各月に1回の支払回を作る |
| 29〜31日がない月 | その月の末日へ寄せる。次の月も短い月の処理結果を基準にせず、元の基準日から算出する |
| 年額 | 元の月日を基準に年1回とする |
| 2月29日の年額 | 平年は2月末、うるう年は元の2月29日とする |
| タイムゾーン | ルールまたは保管庫に明示したタイムゾーンで当日を判定する。serverのOS設定や閲覧端末のUTC変換で支払日をずらさない |
| 金額・口座などの変更 | 変更後の未生成分に適用する。生成済み取引を一括で遡及変更しない |
| 周期・支払日の変更 | 適用開始境界と次回支払日を確認し、生成済みの支払回を別名で二重発行しない |

例えば月額の基準日が31日なら、2月末の次は3月31日とする。年額を月額換算した金額を毎月の取引として登録しない。登録金額は、その支払回に実際に計上する設定額とする。初期版の対象を支出に限定するか、定期収入も扱うかは未決事項に含める。

## 6. 自動生成と障害時の扱い

次回利用時の補完では、保管庫が利用可能になった時点の当日までを対象にする。未来月をカレンダーで開く操作や検索は、取引を作成する契機にしない。

実装提案:

- 有効なルールの未処理の支払回を日付順に処理する。長期未起動・多数ルールに対して件数上限と継続位置を設ける。具体的な上限値は負荷検証で決める。
- ルールIDと安定した支払回IDで一意性を保証する。表示上の日付・項目名・編集revisionの変更だけで同じ支払いを再発行しない。
- 取引、生成元、確認状態、支払回の処理記録、必要な残高再計算を同じledgerトランザクションで確定する。
- 複数画面・複数セッション・再起動後の再処理が競合しても、同じ支払回を1件だけ登録する。
- 永続化前の失敗は未処理として再試行できるようにする。成功した支払回を後続の失敗によって重複登録しない。
- 利用者が生成済み取引を削除した場合の初期提案は、同じ支払回を勝手に再作成しない方式とする。削除済みの処理記録の保持と明示的な再作成操作の要否をレビューする。

自動登録を停止しても、生成済み取引・その確認状態・生成元を削除しない。停止中に生成済みの過去取引を開いて保存した場合も、通常表示への変更を妨げない。

## 7. 月表示カレンダー

最初は当月を表示し、前月・翌月への移動を繰り返せるようにする。任意の年月を直接選ぶ操作も実装提案とする。過去・未来への移動を隣接月だけに制限しない。週表示・日表示は追加しない。

支払日に項目名・金額などを表示し、同じ日に複数のサブスクがある場合もそれぞれ確認できるようにする。未来の表示はルールから算出した予定とし、取引IDを持つ登録済み取引として保存・集計しない。

登録済みの支払回は、予定と実績を重複して2件表示しない。登録済みの項目からは既存の取引画面を開き、未来の予定からは対応するルール・予定の詳細を確認する。未来の予定を開く操作で取引を前倒し登録しない。

停止・金額変更・周期変更の前後で、過去月の実績が現在の設定値に置き換わらないようにする。過去に実際の登録がない予定を支払済み実績として扱わない。自動登録取引の確認状態を説明する文字や専用色はカレンダーにも追加しない。

## 8. サブスク候補の提案

提案は、利用者が自動登録を明示指定するきっかけとして提供する。候補判定だけでルールを作成したり、取引を登録したりしない。承認する際には、周期・次回支払日・金額・口座などを確認してから登録する。

初期アルゴリズムの提案は、同じ口座・項目名、近い金額、月または年単位の繰り返しなどを使うルールベースの判定とする。最低履歴件数、日付・金額の許容幅、表記ゆれ、候補の並び順は未決であり、テスト用の履歴を使って決める。年額は十分な過去履歴がない場合に判定できないことも考慮する。

自動生成した取引を候補判定の根拠にして提案を自己増殖させない。既存ルールと重なる提案、保存受付の再送、クレジットカードと引落口座の両側を別のサブスクと誤認するケースを検証する。拒否した候補の再表示方針も決める。

履歴を外部の学習サービスへ送る方式は、この初期提案に含めない。機械学習モデル、学習方法、新しい依存の導入は、必要性と精度を確認して別途判断する。既存のproduction AI非提供の境界を変更する承認とは扱わない。

## 9. データと既存実装への接続

物理テーブル名・API名は後続の設計PRで決める。必要となる概念は以下のとおり。

| 概念 | 保持する内容 |
| --- | --- |
| サブスクルール | 安定したID、周期、基準日・次回支払日、金額、口座・項目名・種別・メモ・タグのテンプレート、有効・停止、更新の適用境界 |
| 支払回の記録 | 重複防止用の支払回ID、元の予定日、適用したルールの版、生成した取引との対応、削除後も再生成を防ぐための記録 |
| 取引の生成元 | 手動登録との区別とルールID。確認後や個別編集後も保持する |
| 取引の確認状態 | 薄い表示を適用するかどうか。集計対象から除外するフラグにはしない |
| 候補判定・拒否記録 | 過剰な再提案を防ぐための必要最小限の情報。具体的な保持範囲は後続PRで決める |

既存取引への移行では、手動登録済みのデータを自動生成扱いに変更しない。既存の金額精度・入力検証・残高再計算を利用する。画像や取引間の紐付けをテンプレートから毎回複製する方式は初期提案に含めない。

[既存のtransaction_links](../../backend/models/models.go)はクレジットカードと銀行口座の照合に使用するため、サブスクの生成元を表す用途へ転用しない。serverの[取引保存受付](../../backend/database/transaction_save_schema.go)と、[SQLite書き込み予約](../sqlite-write-concurrency.md)の整合性を維持する。

Desktopとmulti-user serverで同じドメイン仕様を使う。サブスク情報・予定・候補・処理記録は本人の暗号化ledger/vault内で扱う。control DB、共有の平文設定、ブラウザの永続ストレージへ明細や復号鍵を複製しない。

serverでは認証済みの本人のvault leaseを利用する。他ユーザーや管理者のために保管庫を復号する経路を追加しない。Desktopのロック、serverのログアウト・lease失効・復元時には生成処理を適切に止める。ロック中も書き込むために鍵を保持し続ける設計にはしない。

## 10. CSV・snapshot・復元

既存CSV v3の表現だけでサブスクルールや確認状態が復元できると仮定しない。CSVの互換性・追加情報の表現・append/replace時の生成元IDの扱いを、DB変更と合わせて設計する。対応する形式の版を更新するか、明示的に範囲を区別するかは未決事項とする。未決のままmain統合を完了しない。

snapshotには取引・ルール・支払回の重複防止記録を一貫した状態で含める。復元後の補完で重複を生まないことを検証する。復元によって時点が戻るという既存契約を維持し、生成処理と復元処理を競合させない。

## 11. 段階的なPRの案

各作業用ブランチから`feat/manage-subscription`へPRを作成する。mainへ直接機能を小分けに投入しない。各段階の実装着手は利用者の依頼に従い、本書の作成だけを後続実装の自動開始指示としない。

| 段階 | レビューする範囲 |
| --- | --- |
| 1 | 本仕様書。確定条件・実装提案・未決事項を区別する |
| 2 | データモデル、schema migration、周期計算、CSV・復元方針 |
| 3 | 本人のvaultでの生成処理、重複防止、停止・補完、集計への反映 |
| 4 | 明示指定と一元管理、停止操作、生成元での検索 |
| 5 | 透明度だけによる表示、既存保存操作との連携、確認状態の永続化 |
| 6 | 過去・未来へ移動できる月表示カレンダー |
| 7 | 候補提案、誤提案・拒否・重複の扱い |
| 8 | Desktop/serverの統合検証、恒久ドキュメントの更新、開発用文書の整理、main向けPR |

既存のCIを維持し、必要なテストを各実装PRで追加する。mainの修正を適宜取り込み、最終main向けPRは最新mainと整合した状態にする。機能追加としてのVERSION更新は、その時点のmainを基準に別途判断する。CI/CDの継続監視・マージは、利用者から依頼がある場合だけ行う。

## 12. 受入条件

| 対象 | 確認する結果 |
| --- | --- |
| 月額・年額 | 各周期に従い、当日までの分だけが生成される |
| 未来の予定 | カレンダーの移動・閲覧では取引も残高も増えない |
| 未起動・ロック | 次回利用可能になったときに未登録分を補い、鍵なしで処理を進めない |
| 集計 | 薄く表示された自動登録取引も、通常取引と同じ金額・符号で残高・収支へ反映される |
| 表示 | 確認状態の説明文言・バッジ・専用色を追加せず、透明度のみで薄く表示する |
| 保存 | 開くだけ・取消・失敗では薄いまま。変更なしの保存成功でも通常表示になる |
| 永続性 | 再起動・再ログイン後も、通常表示への変更と生成元を保持する |
| 停止 | 以後の生成だけが止まり、生成済みの過去取引・検索・集計を保持する |
| 検索 | 名前の一致ではなく指定ルールの自動生成分だけが表示され、編集・確認後も追跡できる |
| 重複 | 同時利用・再試行・途中失敗でも同じ支払回を重複登録しない |
| 日付 | 短い月・うるう年・年越し・タイムゾーン・周期変更の境界で日付と件数が正しい |
| 分離 | 別ユーザーのルール・履歴・候補へアクセスできず、停止・復元・ログアウトが安全に競合する |
| 移行と復元 | 既存取引の値と表示を保ち、CSVとsnapshotについて決めた復元契約を満たす |
| 提案 | 承認前の自動登録がなく、誤提案・拒否・既存ルールとの重複を制御できる |

## 13. 実装前に決める事項

残高への算入、文字による状態説明の禁止、色味を変えない透明度表示、当日までの生成と次回利用時の補完は確定済みであり、この未決事項には含めない。

- 初期対象を支出に限定するか。ルールの新規作成を既存取引以外からも許すか。
- 元の取引を登録済みの支払回として扱う方法、最初の自動生成日、過去分の遡及登録を許す範囲。
- 短い月・2月29日の扱い、タイムゾーン設定の置き場、周期変更の適用開始境界。
- 停止からの再開、生成済み取引を削除した回、既存の手動・CSV取引と同じ支払いがある場合の扱い。
- 透明度の具体値、管理画面・カレンダーの配置と操作、候補の表示頻度と拒否後の再表示。
- ルール数・補完件数・取得年月範囲の上限とページング。候補判定の最低件数と許容幅。
- CSVの形式・可搬性とsnapshot復元後の生成契約。
