# SQLite書き込み競合の調査と対処

タグパスの並列作成で発覚したロックエラーを起点に、ledger・control DBの更新、読み取り、スナップショット、復元、移行のSQL経路を確認しました。Desktopとserverは同じcore実装を使います。serverの異なる利用者のvaultは別DBです。

## 更新処理の開始

SQLiteのWALモードでは読み取りと書き込みを並行できますが、同じDBへの書き込みは一度に一つです。通常のトランザクションで先に読み取ると、後から書き込みへ移る際に古いスナップショットや競合が原因で、`busy_timeout`の待機を使えず失敗する場合があります。

ledgerの更新トランザクションは`beginLedgerWrite`を通し、検証・検索より前に書き込み予約を取得します。`database/sql`の`*sql.Tx`を維持するため、開始直後に`DELETE FROM transaction_links WHERE 0`を実行します。削除対象は常に0件で、行トリガーも実行されません。これは既存の紐付け処理で使っていた方式の共通化であり、書き込み予約の取得は`BEGIN IMMEDIATE`と同じです。キャンセル、prepared statement、commit/rollbackは引き続き`database/sql`が管理します。

同じDBの先行書き込みが完了してから状態を読み取り、判断・更新・確定を同じトランザクション内で行います。別vaultに対するアプリ全体のmutexや、接続プールを一つに制限する変更はありません。画像の変換やCSVの解析は引き続き予約取得前に行います。

| 調査した経路 | 対応・確認結果 |
| --- | --- |
| 取引追加・編集・削除、残高再計算 | 共通の書き込み予約を使用。タグ・画像・紐付け・残高は既存の取引トランザクション内で更新 |
| 保存受付と非同期の保存反映 | 受付ID・件数・状態の確認前に予約。再送識別、受付の永続化、反映と完了記録の原子性を維持 |
| 画像追加 | 容量・件数の照合前に予約 |
| タグ作成・改名・削除・取引への追加 | 存在・階層・重複の照合前に予約。パス作成も共通処理を使用 |
| クレジットカード・銀行口座設定、取引紐付け | 設定や既存割当の照合前に予約 |
| CSV append/replace、旧形式、プレビュー付き取り込み | 整合性・容量・取込先digestの照合前に予約。待機中の変更を取り込み開始後に再確認 |
| 非公開の旧AI取引保存実装 | 他の取引保存と同じ共通処理を使用。production提供の変更なし |
| control DBのパスキー登録 | 件数確認前に既存の`withImmediate`を使用。待機中の登録を含めて上限を判定 |
| bootstrap、invite/reset消費、認証情報・権限変更、login throttle | 既存の`withImmediate`を維持。rollbackに失敗した接続は再利用しない |
| パスキー使用記録 | 最初のSQLがrevisionを条件としたUPDATEであり、読み取りからの昇格はない。既存のCASとトランザクションを維持 |
| 単一SQLの画像変更・削除、タグ解除、紐付け解除など | autocommitの書き込みが開始時に予約を取得。既存の5秒の待機設定を維持 |
| CSV出力・プレビュー、照合集計、一覧・検索 | 書き込み予約を加えない。既存の読み取り専用トランザクションとrows解放を維持 |
| スキーマ初期化・復元候補の移行 | 通常リクエストへDBを公開する前、または非公開の復元候補に対して実行。オンラインの更新経路とは分離 |
| スナップショット作成 | 既存のonline backupとbusy時の再試行・キャンセルを維持。raw SQLite接続や暗号化openerを変更しない |
| 復元・平文からの暗号化移行 | WAL checkpointの結果行も確認。busyで未完了ならファイル差し替えへ進まない |

## WAL checkpointの未完了

`PRAGMA wal_checkpoint(TRUNCATE)`は、他の接続が読み取り中などで完了できない場合、SQLエラーではなく結果行の先頭列でbusyを通知します。`Exec`のエラーだけを見ても完了は証明できません。

`securedb.CheckpointTruncate`で結果行を読み取り、busyをSQLiteのbusyエラーとして返します。live DBの復元前、復元候補を閉じる前、平文からの暗号化移行前で使います。live DBのcheckpointに失敗した復元は、元の接続とデータを保持したまま中止します。通常のsnapshot/restoreのドレイン処理も維持します。

## 回帰検証と範囲

- 14種類のledger更新とパスキー登録は、競合する書き込みを明示的に保持した再現テストで修正前の即時失敗を確認しました。修正後は予約待ちの後に処理します。
- 待機中のCSV取込先の変更はプレビュー不一致として拒否し、パスキー件数の増加は登録上限に反映します。
- 保存受付の8並列再送テストからテスト側の再試行を除きました。同じIDの再送識別は維持します。
- 書き込み中でもCSV出力・プレビューが進むこと、別vaultの独立性、キャンセル・途中失敗時のrollbackと接続解放を検証します。
- 読み取り接続でWALを保持した復元は、修正前には成功扱いで先へ進んでいました。修正後は現在のデータを保持して中止し、読み取り終了後の復元が成功することを検証します。
- 暗号化ledgerでも同じ14ケースを実行するテストを用意し、固定SQLCipherを使用するCI段階に追加しました。通常SQLiteのローカル実行を暗号化の検証結果として扱いません。

書き込みの順序を正しく調整する修正です。長時間の書き込みや別プロセスのロックが既存の待機上限を超える場合、I/O障害などの場合には引き続きエラーを返します。全SQLを無条件に再実行する処理は加えていません。

参考: [SQLiteのトランザクション分離](https://www.sqlite.org/isolation.html)、[busy handlerの制約](https://www.sqlite.org/c3ref/busy_handler.html)、[WAL checkpointの結果](https://www.sqlite.org/pragma.html#pragma_wal_checkpoint)。
